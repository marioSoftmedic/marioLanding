## Hook: The Day an Autonomous Agent Quoted the Same Prescription Three Times

In Twitter demos and academic benchmarks, "autonomous agents" powered by ReAct (*Reason + Act*) loops look like magic. You give them a natural language goal, provide five tools (`search_catalog`, `parse_prescription`, `calculate_pricing`, `create_payment_link`, `send_whatsapp`), and the model supposedly figures out what to do next.

We fell straight into that trap when we started building **Examya**.

We assumed that the flexibility of frameworks like LangChain or CrewAI would easily accommodate the chaotic, unstructured nature of patient messages over WhatsApp. Then production hit.

One Friday morning, a patient sent a blurry photo of a handwritten medical prescription containing three blood tests. The LLM wasn't 100% confident about two of the clinical codes, called the catalog search tool with ambiguous query parameters, and entered an internal reflection loop to self-correct. Meanwhile, the patient sent a follow-up text: *"Sorry, can you read that okay?"*.

That single follow-up message broke the agent's context assumptions. The LLM re-evaluated the entire conversation from scratch, triggered two concurrent tool calls to the pricing engine, generated two different payment links with a price discrepancy due to fee hallucinations, and sent three contradictory WhatsApp messages in under four seconds.

That was the day we learned an uncomfortable engineering truth: **in transactional and clinical workflows, probabilistic control flow isn't an advantage; it is operational negligence.**

---

## Anatomy of a Failure: Why Agent Frameworks Break in Real-World Messaging

Popular agent frameworks were architected on three assumptions that crumble in production:

1. **They assume synchronous, turn-based dialogue:** In WhatsApp, humans don't wait for your agent to finish "thinking". They send voice notes, images, text corrections, and question marks within a 15-second window. An open-loop ReAct agent collapses under out-of-order events.
2. **They confuse data reasoning with workflow orchestration:** Letting an LLM decide which business logic step executes next is the architectural equivalent of replacing your HTTP router with a weighted random number generator.
3. **They lack deterministic rollback boundaries:** When an external tool fails midway through an autonomous sequence (e.g., a timeout in a hospital's legacy LIS), the agent attempts to "talk its way out" instead of executing an atomic database rollback.

In a B2C productivity app, a 25-second hallucinated loop is mildly annoying. In healthcare, charging the wrong fee, scheduling a procedure without verifying fasting requirements, or confirming an order with invented diagnostic codes violates compliance laws and incinerates trust.

## The Architectural Solution: FSM in the Trunk, LLM in the Leaves

We threw away the autonomous loop and rebuilt Shuri's conversational engine around one strict rule:

> **The LLM operates exclusively at the leaves of the tree (data extraction and text generation). The control trunk is a 100% deterministic Finite State Machine (FSM).**

```
                   INCOMING WHATSAPP EVENT
                              │
                              ▼
              ┌───────────────────────────────┐
              │    Redis Concurrency Lock     │  (Prevents race conditions)
              └───────────────┬───────────────┘
                              │
                              ▼
              ┌───────────────────────────────┐
              │   Finite State Machine (FSM)  │  (Defines valid transitions)
              │     Current Stage: QUOTING    │
              └───────────────┬───────────────┘
                              │
          ┌───────────────────┴───────────────────┐
          ▼                                       ▼
┌───────────────────┐                   ┌───────────────────┐
│   LLM Worker 1    │                   │   LLM Worker 2    │
│(OCR / Zod Schema) │                   │(Message Generation│
└───────────────────┘                   └───────────────────┘
  Extracts typed data                     Drafts empathetic response
  CANNOT alter workflow                   CANNOT alter workflow
  state transitions                       state transitions
```

### How It Works in Code

Every WhatsApp session maintains a transactional state persisted in PostgreSQL (`INITIAL`, `ORDER_RECEIVED`, `EXTRACTING_EXAMS`, `CONFIRMING_QUOTATION`, `PAYMENT_PENDING`, `COMPLETED`).

No incoming user event can bypass a state without satisfying strict transition guards. The LLM is invoked only for pure transformation tasks:

```typescript
// ShuriStateMachine: Deterministic workflow control
export interface ConversationState {
  currentStage: 'INITIAL' | 'ORDER_RECEIVED' | 'QUOTING' | 'PAYMENT_PENDING';
  extractedData?: MedicalOrderSchema;
}

export async function handleIncomingMessage(
  session: Session,
  message: WhatsAppMessage
): Promise<void> {
  const currentState = session.state;

  switch (currentState.currentStage) {
    case 'ORDER_RECEIVED':
      // The LLM ONLY extracts data against a strict Zod schema
      const extracted = await extractMedicalOrderWithZod(message.mediaUrl);
      
      if (!extracted.isValid) {
        // The FSM decides the transition, not the model
        await transitionTo(session, 'MANUAL_REVIEW_REQUIRED');
        return;
      }
      
      // State transition governed purely by deterministic business logic
      await transitionTo(session, 'QUOTING', { data: extracted.order });
      break;

    case 'QUOTING':
      // Direct call to clinical fee database (no LLM in the middle)
      const quote = await calculateFonasaPricing(session.data.exams);
      await sendDeterministicQuotation(session, quote);
      await transitionTo(session, 'PAYMENT_PENDING');
      break;

    default:
      await handleFallbackState(session);
  }
}
```

## Three Immediate Production Wins

### 1. Latency and API Costs Dropped by 68%
An autonomous ReAct agent typically runs 3 to 5 LLM calls per turn (Plan → Think → Act → Observe → Respond). With an FSM, our backend already knows whether an LLM is even required or if a cached SQL query and static response suffices. We dropped response times from 12 seconds to under 2.2 seconds.

### 2. True Idempotency Under Burst Messaging
When a patient sends four photos in rapid succession, the FSM acquires a Redis distributed lock based on their phone number. The first photo transitions the state to `ORDER_PROCESSING`. The subsequent three photos append as attachments to the active ticket without spinning up four rogue agents fighting for control.

### 3. Auditable Compliance and Traceability
When a healthcare partner asks: *"Why was this patient charged this exact fee on this date?"*, we don't have to parse through unformatted LLM reasoning traces. We have an immutable relational audit log:
* `2026-09-25 11:30:02` — Event: `IMAGE_RECEIVED` → State: `ORDER_RECEIVED`
* `2026-09-25 11:30:04` — Event: `OCR_PARSED` (Confidence: 0.96) → State: `QUOTING`
* `2026-09-25 11:30:05` — Event: `PRICING_CALCULATED` (FONASA Tier 3) → State: `PAYMENT_PENDING`

## Lessons for AI Builders in Production

If you are building AI software for mission-critical domains (healthcare, fintech, legal, logistics):

1. **Beware of "total autonomy" frameworks:** Unbounded agent autonomy is a blast for weekend hackathons, but a nightmare in production.
2. **Enforce strict schemas (Zod, Pydantic) on every model output:** If the LLM cannot return clean JSON conforming to your schema on the first attempt, fall back deterministically—never let the agent improvise conversational recovery.
3. **Application state belongs in your database, not inside the prompt:** Prompts are volatile. Relational state machines are your only defense against network timeouts, dropped connections, and provider outages.

Real engineering sophistication in AI is not about letting the model run free. It is about building precise guardrails so the model excels at what it does best—extracting meaning and structuring language—while deterministic code retains absolute control over execution.
