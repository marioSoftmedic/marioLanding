En operaciones de turismo y hospitalidad en zonas remotas como la Patagonia, una sobreventa (*overbooking*) no es una simple molestia administrativa: es un fallo logístico mayor. Si dos viajeros reservan la misma cabaña para el mismo fin de semana porque tu agente conversacional de WhatsApp y tus canales de agencias de viaje online (OTAs como Airbnb y Booking) no están sincronizados de forma atómica, terminas con una familia en la puerta sin un lugar donde dormir a cientos de kilómetros de la ciudad más cercana.

Cuando incorporas un agente de inteligencia artificial para gestionar reservas directas por WhatsApp, la velocidad de respuesta es tu mayor ventaja comercial, pero también tu mayor riesgo de concurrencia. Mientras el agente dialoga con el usuario para recopilar fechas y datos de los huéspedes, el inventario sigue expuesto en plataformas externas cuyos feeds de calendario iCal se refrescan de manera asíncrona con desfases de varios minutos.

La solución instintiva de muchos equipos de ingeniería suele ser defectuosa: agregan consultas frecuentes sin control (*polling*) a los calendarios externos o intentan bloquear tablas enteras en la base de datos cada vez que un usuario saluda por chat.

En este artículo explico la arquitectura que construimos para resolver la sincronización multi-canal de inventario entre WhatsApp y OTAs: cómo implementar una capa de transporte seguro con límites estrictos, cómo estructurar el agente como una máquina de estados determinística y cómo aplicar el patrón **Cabin-First Lock** para garantizar consistencia transaccional sin colapsar el sistema.

## El problema del inventario desincronizado en tiempo real

El protocolo iCal (`.ics`) es el estándar universal adoptado por plataformas como Airbnb, Booking.com y VRBO para intercambiar calendarios de disponibilidad. Aunque es simple y portable, iCal tiene una limitación fundamental de diseño: **es un protocolo de sondeo pasivo (*pull*), no una interfaz de notificación en tiempo real (*push*)**.

Esto genera una asimetría operacional inevitable:
1. Un huésped consulta disponibilidad por WhatsApp para la Cabaña 2 entre el 15 y el 18 de noviembre.
2. Tu backend consulta la base de datos interna y confirma que el rango de fechas está desocupado.
3. Mientras el usuario envía sus datos y el agente redacta la confirmación (un intervalo que puede tomar de 30 segundos a 5 minutos), una reserva sobre esa misma cabaña entra directamente por Airbnb.
4. Airbnb no avisa a tu servidor mediante un webhook instantáneo; tu servidor solo se enterará cuando ejecute su siguiente ciclo de sondeo iCal, que típicamente ocurre cada 15 a 60 minutos para evitar bloqueos por cuota de peticiones.
5. El agente de WhatsApp confirma la reserva localmente y exporta el nuevo bloqueo a su propio feed iCal saliente, pero Airbnb ya cerró la reserva en su plataforma.

El resultado es una colisión de inventario directa. Ningún prompt ingenioso en un modelo de lenguaje puede evitar esta condición de carrera (*race condition*) si la arquitectura de datos subyacente no aísla las transacciones de manera determinística.

## Por qué los enfoques ingenuos fallan en producción

Frente a este escenario, es común observar tres antipatrones recurrentes en integraciones de hospitalidad:

### 1. Polling agresivo sin límites de transporte
Para reducir la ventana de colisión, algunos sistemas configuran tareas programadas (*cron jobs*) que descargan feeds iCal cada 30 segundos. Las consecuencias son inmediatas: las APIs de las OTAs activan respuestas `429 Too Many Requests`, las direcciones IP del servidor quedan bloqueadas y los servidores quedan expuestos a ataques de denegación de servicio si un calendario externo devuelve un archivo sobredimensionado o malformado.

### 2. Bloqueos globales de base de datos
Otro error habitual es ejecutar bloqueos a nivel de tabla durante la consulta de disponibilidad. Si diez usuarios interactúan simultáneamente por WhatsApp preguntando por distintas cabañas o servicios adicionales, todas las peticiones compiten por el mismo recurso de base de datos, elevando la latencia de respuesta y degradando la experiencia conversacional.

### 3. Delegar la consistencia al LLM
Permitir que un modelo de lenguaje interprete el calendario en texto plano dentro del contexto del prompt y decida si una fecha está libre genera alucinaciones de disponibilidad. Un agente conversacional debe delegar el 100% de la lógica de disponibilidad y cálculo de fechas a funciones determinísticas fuertemente tipadas.

## Capa 1: Transporte seguro con Safe Fetch y DNS Pinning

El primer componente crítico es la ingesta de calendarios externos. Cuando un sistema consume URLs de iCal configuradas por operadores o plataformas de terceros, se expone a vulnerabilidades de falsificación de peticiones del lado del servidor (*Server-Side Request Forgery* o SSRF), descargas infinitas y agotamiento de sockets.

Diseñamos un módulo de transporte seguro (`safe-fetch.ts`) con cuatro salvaguardas no negociables:
- **Validación estricta de protocolo:** Solo se permiten conexiones HTTPS seguras.
- **Resolución DNS y fijación de IP (*DNS Pinning*):** Se resuelve la dirección IP del host antes de emitir la petición y se rechazan rangos privados (RFC 1918), direcciones de bucle local (`127.0.0.1`) y metadatos de proveedores en la nube (`169.254.169.254`).
- **Límite duro de tiempo (*Deadline*):** La petición aborta automáticamente tras 12 segundos mediante `AbortSignal.timeout`.
- **Límite de tamaño de payload (*Body Cap*):** El flujo de bytes entrante se corta de inmediato si supera 1 MiB, evitando bombas de descompresión o consumo desmedido de memoria RAM.

```typescript
// infrastructure/transport/safe-fetch.ts
import { lookup } from 'node:dns/promises';
import { isIP } from 'node:net';

const MAX_PAYLOAD_BYTES = 1024 * 1024; // 1 MiB
const REQUEST_TIMEOUT_MS = 12000; // 12 segundos

const FORBIDDEN_IP_RANGES = [
  /^127\./,
  /^10\./,
  /^172\.(1[6-9]|2[0-9]|3[0-1])\./,
  /^192\.168\./,
  /^169\.254\./,
  /^0\./,
  /^::1$/,
  /^fc00:/,
  /^fe80:/
];

function isPrivateIp(ip: string): boolean {
  return FORBIDDEN_IP_RANGES.some((regex) => regex.test(ip));
}

export async function safeFetchIcal(targetUrl: string): Promise<string> {
  const url = new URL(targetUrl);
  if (url.protocol !== 'https:') {
    throw new Error(`Protocolo no permitido: ${url.protocol}. Se requiere HTTPS.`);
  }

  const { address } = await lookup(url.hostname);
  if (!address || isPrivateIp(address)) {
    throw new Error(`Destino bloqueado por seguridad: IP no permitida (${address ?? 'desconocida'}).`);
  }

  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), REQUEST_TIMEOUT_MS);

  try {
    const response = await fetch(url.toString(), {
      signal: controller.signal,
      headers: {
        'User-Agent': 'EstepaSyncEngine/2.0 (Resilience; +https://mariohealthbits.dev)'
      }
    });

    if (!response.ok) {
      throw new Error(`Error HTTP ${response.status} al sincronizar feed.`);
    }

    const reader = response.body?.getReader();
    if (!reader) {
      throw new Error('Cuerpo de respuesta no disponible para lectura.');
    }

    let receivedBytes = 0;
    const chunks: Uint8Array[] = [];

    while (true) {
      const { done, value } = await reader.read();
      if (done) break;

      receivedBytes += value.length;
      if (receivedBytes > MAX_PAYLOAD_BYTES) {
        await reader.cancel();
        throw new Error(`Payload excede el límite máximo de ${MAX_PAYLOAD_BYTES} bytes.`);
      }
      chunks.push(value);
    }

    const buffer = Buffer.concat(chunks);
    return buffer.toString('utf-8');
  } finally {
    clearTimeout(timeoutId);
  }
}
```

## Capa 2: El patrón Cabin-First Lock y la gestión de estados

Para resolver la concurrencia entre la interacción humana en tiempo real y las sincronizaciones en segundo plano, implementamos el patrón **Cabin-First Lock**.

En lugar de considerar que una reserva existe únicamente cuando está pagada o confirmada, el sistema maneja tres estados de ocupación por cabaña:
1. `HOLD` (Bloqueo temporal preventivo): Se adquiere en milisegundos cuando el usuario en WhatsApp selecciona fechas válidas. Tiene un tiempo de vida (*Time-To-Live* o TTL) de 15 minutos.
2. `CONFIRMED` (Reserva consolidada): Se activa cuando se confirma la pre-reserva o se valida el comprobante de pago.
3. `EXTERNAL_BLOCK` (Bloqueo externo): Proviene de eventos parseados desde feeds iCal de Airbnb o Booking.

La regla de oro del patrón es que el bloqueo se aplica **a nivel de recurso individual (la cabaña específica) y no a nivel global**. Esto se logra mediante transacciones aisladas en PostgreSQL utilizando `SELECT ... FOR UPDATE` sobre la fila de la cabaña, evaluando la no superposición de rangos de fechas (`daterange`):

```typescript
// domain/services/cabin-occupancy-transaction.ts
import { PoolClient } from 'pg';

export interface HoldRequest {
  readonly cabinId: string;
  readonly checkIn: string; // Formato YYYY-MM-DD
  readonly checkOut: string; // Formato YYYY-MM-DD
  readonly channel: 'whatsapp' | 'airbnb' | 'booking';
  readonly ttlMinutes: number;
}

export interface HoldResult {
  readonly success: boolean;
  readonly holdId?: string;
  readonly conflictReason?: string;
}

export async function acquireCabinHold(
  client: PoolClient,
  request: HoldRequest
): Promise<HoldResult> {
  await client.query('BEGIN');

  try {
    // 1. Bloqueo pesimista sobre el registro de la cabaña específica
    const cabinRes = await client.query(
      'SELECT id, name FROM cabins WHERE id = $1 FOR UPDATE',
      [request.cabinId]
    );

    if (cabinRes.rowCount === 0) {
      await client.query('ROLLBACK');
      return { success: false, conflictReason: 'Cabaña no encontrada.' };
    }

    // 2. Comprobar superposiciones activas (CONFIRMED, EXTERNAL_BLOCK o HOLD vigentes)
    const overlapRes = await client.query(
      `SELECT id, status, source_channel, check_in, check_out 
       FROM cabin_occupancies
       WHERE cabin_id = $1
         AND daterange(check_in, check_out, '[)') && daterange($2::date, $3::date, '[)')
         AND (status IN ('CONFIRMED', 'EXTERNAL_BLOCK') 
              OR (status = 'HOLD' AND hold_expires_at > NOW()))`,
      [request.cabinId, request.checkIn, request.checkOut]
    );

    if (overlapRes.rowCount && overlapRes.rowCount > 0) {
      const conflict = overlapRes.rows[0];

      // Registrar el conflicto de ocupación sin almacenar datos personales (PII)
      await client.query(
        `INSERT INTO occupancy_conflicts 
         (cabin_id, source_channel, conflicting_channel, requested_range, detected_at)
         VALUES ($1, $2, $3, daterange($4::date, $5::date, '[)'), NOW())`,
        [request.cabinId, request.channel, conflict.source_channel, request.checkIn, request.checkOut]
      );

      await client.query('COMMIT');
      return {
        success: false,
        conflictReason: `Conflicto de fechas con reserva existente (${conflict.status}).`
      };
    }

    // 3. Insertar el nuevo HOLD con TTL
    const insertRes = await client.query(
      `INSERT INTO cabin_occupancies 
       (cabin_id, status, source_channel, check_in, check_out, hold_expires_at, created_at)
       VALUES ($1, 'HOLD', $2, $3::date, $4::date, NOW() + ($5 || ' minutes')::interval, NOW())
       RETURNING id`,
      [request.cabinId, request.channel, request.checkIn, request.checkOut, request.ttlMinutes]
    );

    await client.query('COMMIT');
    return {
      success: true,
      holdId: insertRes.rows[0].id
    };
  } catch (error) {
    await client.query('ROLLBACK');
    throw error;
  }
}
```

## Capa 3: Registro de colisiones y auditoría operacional sin PII

Cuando una colisión ocurre, el sistema no debe fallar en silencio ni registrar datos sensibles en los logs. El esquema de auditoría utiliza una tabla dedicada `occupancy_conflicts` que almacena exclusivamente metadatos estructurales: identificador de cabaña, canales involucrados, rango de fechas en conflicto y marca temporal.

Esto entrega visibilidad completa para métricas operacionales:
- Frecuencia de colisiones por canal (WhatsApp vs Airbnb vs Booking).
- Horarios pico de contención de inventario.
- Tasa de conversión de bloqueos `HOLD` a reservas confirmadas `CONFIRMED`.

Al excluir números de teléfono, nombres y detalles de tarjetas de crédito del log de auditoría técnica, el sistema cumple con estándares estrictos de protección de datos y facilita el análisis de telemetría sin comprometer la privacidad del viajero.

## Gotchas de producción y el camino hacia Channel Managers

Durante meses de operación real en la Patagonia, aprendimos lecciones críticas sobre los límites del protocolo iCal:

1. **Desfase asimétrico de refresco:** Mientras tu servidor puede exportar cambios en tiempo real, Booking y Airbnb refrescan sus conexiones externas con periodicidades dispares (entre 15 minutos y 3 horas según la demanda). La única protección real contra ese intervalo ciego es el bloqueo temporal preventivo (`HOLD`) inmediato en tu propio motor de inventario.
2. **El problema de las zonas horarias y el cambio de hora:** Los feeds iCal expresan fechas en UTC (`VALUE=DATE` o `DTSTART:YYYYMMDDTHHMMSSZ`). Si tu base de datos o el agente de WhatsApp realiza conversiones ingenuas sin fijar explícitamente la zona horaria local (`America/Santiago` o `America/Punta_Arenas`), una reserva de 3 noches puede desplazarse un día completo al cruzar la medianoche UTC o durante la transición de horario de verano.
3. **Eventos cancelados que reaparecen:** Algunas plataformas no eliminan eventos cancelados de sus feeds, sino que cambian su estado a `STATUS:CANCELLED` o simplemente omiten el UID en la siguiente descarga. El parser debe manejar reconciliación diferencial: si un evento previamente importado desaparece del feed entrante, debe liberarse de forma segura tras verificar que no corresponda a un fallo de red transitorio.

Cuando un operador turístico supera las 10 o 15 unidades de alojamiento, el protocolo iCal alcanza su límite funcional. En ese punto, la arquitectura modular que diseñamos permite sustituir el adaptador de transporte `safe-fetch.ts` por adaptadores API directos hacia Channel Managers (como Beds24 o Channex), manteniendo intacto el núcleo de dominio, la máquina de estados y las garantías de bloqueo transaccional.

## Lecciones operacionales

Construir un agente conversacional para WhatsApp en hospitalidad no consiste en conectar un modelo de lenguaje a una base de datos abierta. Consiste en construir un sistema de inventario robusto donde el modelo de lenguaje actúa únicamente como una interfaz de traducción de lenguaje natural.

Las tres reglas fundamentales que guían esta arquitectura son:
1. **Los contratos de transporte deben ser defensivos:** Validar IPs, aislar protocolos, fijar timeouts cortos y restringir el tamaño de los feeds entrantes.
2. **Las transacciones mandan sobre las conversaciones:** El agente nunca debe prometer una cabaña a un usuario antes de haber adquirido un bloqueo atómico temporal en la base de datos.
3. **Auditoría limpia y determinismo:** Registrar cada colisión sin datos sensibles y tratar la sincronización de inventario como un problema de consistencia transaccional y no como un problema de prompting.
