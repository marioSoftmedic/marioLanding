Viernes por la tarde. El pipeline de Integración Continua muestra todos los indicadores en verde brillante. La suite de pruebas unitarias marca con orgullo un 100% de cobertura de código: cada rama condicional, cada controlador y cada servicio de dominio tiene una prueba asociada que pasa sin vacilar.

El equipo aprueba el pull request, la imagen de contenedor se construye y el orquestador inicia el despliegue hacia producción. Treinta segundos después, las alarmas de monitoreo inundan el canal de incidentes: el nuevo contenedor entra en un bucle de reinicios constantes (`CrashLoopBackOff`) y el proceso principal muere antes de escuchar la primera petición HTTP.

Al abrir los logs de la terminal, aparece el temido mensaje del contenedor de Inversión de Control:

```text
[Nest] 1  - 10/09/2026, 5:02:14 PM   ERROR [ExceptionHandler] Nest can't resolve dependencies of the PatientNotificationService (?). Please make sure that the argument at index [2] is available in the NotificationModule context.

Potential solutions:
- Is NotificationModule importing the module that exports the requested provider?
- Did you add the provider to the "providers" list of NotificationModule?
```

¿Cómo es posible que una base de código con 100% de cobertura en sus pruebas unitarias colapse estrepitosamente en el primer milisegundo de su arranque?

La respuesta es incómoda pero fundamental para cualquier arquitecto de software: las pruebas unitarias tradicionales evalúan la lógica interna de tus clases, pero tienen un punto ciego absoluto frente a la estructura del grafo de Inyección de Dependencias (DI).

---

## El espejismo del aislamiento y la trampa del mocking

Para lograr pruebas unitarias rápidas y determinísticas, la práctica estándar de la industria exige aislar la unidad bajo prueba. Si estás probando `PatientNotificationService`, aíslas sus dependencias externas reemplazándolas con dobles de prueba (`useValue`, `jest.mock` o librerías de sustitución como `createMock<T>()`):

```typescript
// tests/patient-notification.service.spec.ts
describe('PatientNotificationService', () => {
  let service: PatientNotificationService;
  let mockSmsGateway: Partial<SmsGateway>;
  let mockTemplateRenderer: Partial<TemplateRenderer>;
  let mockAuditLogger: Partial<AuditLogger>;

  beforeEach(async () => {
    mockSmsGateway = { send: jest.fn().mockResolvedValue({ status: 'delivered' }) };
    mockTemplateRenderer = { render: jest.fn().mockReturnValue('Mensaje listo') };
    mockAuditLogger = { logEvent: jest.fn().mockResolvedValue(true) };

    const moduleRef = await Test.createTestingModule({
      providers: [
        PatientNotificationService,
        { provide: SmsGateway, useValue: mockSmsGateway },
        { provide: TemplateRenderer, useValue: mockTemplateRenderer },
        { provide: AuditLogger, useValue: mockAuditLogger },
      ],
    }).compile();

    service = moduleRef.get<PatientNotificationService>(PatientNotificationService);
  });

  it('debe enviar la notificación y registrar la auditoría correctamente', async () => {
    const result = await service.notifyAppointment('patient-42', '2026-10-10 09:00');
    expect(result.delivered).toBe(true);
    expect(mockSmsGateway.send).toHaveBeenCalledTimes(1);
    expect(mockAuditLogger.logEvent).toHaveBeenCalledTimes(1);
  });
});
```

Esta prueba es limpia, rápida y cubre todas las líneas de negocio de `PatientNotificationService`. Sin embargo, tiene un defecto estructural: **le entrega al contenedor un grafo artificial y preconfigurado a mano**.

En este test, tú le estás diciendo explícitamente al runtime: *"Para este provider, usa este mock; para este otro, usa este stub"*. El motor de NestJS nunca tiene la oportunidad de evaluar si en la aplicación real:

1. `AuditLogger` está exportado en el `AuditModule`.
2. `NotificationModule` importó efectivamente a `AuditModule`.
3. Los tokens dinámicos asíncronos (`ConfigService`, variables de entorno) existen en el contexto global o modular.
4. Existen dependencias circulares entre servicios que bloquean la resolución del árbol.

Tener un 100% de cobertura en tests unitarios solo demuestra que tu lógica funciona cuando todas las dependencias ya están resueltas en memoria. No demuestra que tu aplicación sea capaz de armarse a sí misma en el arranque.

## Anatomía del problema: Por qué falla el contenedor IoC en NestJS

En arquitecturas modulares backend construidas sobre NestJS, el ciclo de vida del arranque (*bootstrap*) ocurre en dos fases críticas antes de que la aplicación acepte tráfico:

```text
FASE 1: RESOLUCIÓN ESTÁTICA DEL GRAFO
AppModule ──> Imports [AuthModule, NotificationModule, AuditModule]
                     │                    │
                     ▼                    ▼
             [SmsGateway (privado)]   [PatientNotificationService]
                                                  │
                                                  ▼ (Requiere AuditLogger)
                                         AuditModule (¿Exports AuditLogger?) ──> ERROR SI NO ESTÁ EXPORTADO

FASE 2: INICIALIZACIÓN DE CICLO DE VIDA (Lifecycle Hooks)
OnModuleInit ──> OnApplicationBootstrap ──> Server.listen()
```

Los tres errores más frecuentes que los unit tests ignoran por completo son:

### 1. El provider privado no exportado
Creas un provider en un módulo compartido (`CommonModule` o `AuditModule`), lo registras en el arreglo `providers`, pero olvidas incluirlo en el arreglo `exports`. Cuando otro módulo importa `AuditModule` e intenta inyectar el servicio, el contenedor colapsa en el arranque porque el provider está encapsulado y es invisible para el exterior.

### 2. Tokens asíncronos y módulos dinámicos mal cableados
Módulos de infraestructura configurados mediante fábricas asíncronas (como conexiones a bases de datos, clientes de colas o proveedores de configuración) que dependen de variables de entorno o parámetros dinámicos. Si un submódulo intenta consumir un token antes de que el módulo raíz lo provea, el arranque falla.

### 3. Dependencias circulares ocultas
Dos módulos o servicios se importan mutuamente. En pruebas unitarias aisladas, cada uno se prueba con mocks y el problema no existe. En producción, la inicialización del contenedor se bloquea en una referencia indefinida (`undefined`) a menos que se use `forwardRef()` de forma explícita y disciplinada.

## El patrón Bootstrap Guardrails: Compilación del contenedor real en CI

Para cerrar esta brecha sin incurrir en el costo de pruebas End-to-End lentas que dependan de bases de datos levantadas o servicios de terceros, implementamos el patrón de **Bootstrap Guardrails**.

Un Bootstrap Guardrail es una prueba automatizada que se ejecuta en el pipeline de CI/CD y compila el módulo raíz (`AppModule`) exactamente con la misma configuración modular que usará en producción, sustituyendo únicamente las fronteras físicas de I/O (conexión TCP de base de datos, puertos HTTP y colas de mensajes) mediante adaptadores nulos o providers anulados (*overrideProvider*).

El objetivo no es probar si la base de datos responde a una consulta SQL, sino responder una sola pregunta determinante: **¿Puede el contenedor de Inversión de Control resolver todas las dependencias del sistema sin errores?**

```text
PIPELINE DE INTEGRACIÓN CONTINUA (CI)

[Lint & Tipos] ──> [Tests Unitarios (Mocks)] ──> [BOOTSTRAP GUARDRAIL] ──> [Build Docker & Deploy]
                                                       │
                                                       ▼
                                          Compila AppModule completo
                                          (Valida grafo de DI en ~350ms)
                                          ¿Falta un export/provider?
                                          ├── SÍ ──> Detiene el build de inmediato en CI
                                          └── NO ──> Pasa al empaquetado seguro
```

## Implementación paso a paso en TypeScript

A continuación se detalla la estructura de un Bootstrap Guardrail para un backend en NestJS.

### Paso 1: Configurar el test de compilación del módulo raíz

Creamos un archivo dedicado `test/app.bootstrap.spec.ts` que importa directamente el `AppModule` de la aplicación:

```typescript
// test/app.bootstrap.spec.ts
import { Test, TestingModule } from '@nestjs/testing';
import { AppModule } from '../src/app.module';
import { INestApplication } from '@nestjs/common';
import { DataSource } from 'typeorm';

describe('Application Bootstrap Guardrail', () => {
  let app: INestApplication;
  let testingModule: TestingModule;

  beforeAll(async () => {
    // Definir variables de entorno sintéticas pero válidas para el arranque
    process.env.NODE_ENV = 'test';
    process.env.PORT = '3000';
    process.env.DATABASE_URL = 'postgresql://synthetic_user:synthetic_pass@localhost:5432/synthetic_db';
    process.env.JWT_SECRET = 'guardrail-secret-key-min-32-characters-length!';

    const moduleFixtureBuilder = Test.createTestingModule({
      imports: [AppModule],
    });

    // Anulamos únicamente la conexión física a la base de datos para no requerir un motor activo en CI
    moduleFixtureBuilder.overrideProvider(DataSource).useValue({
      isInitialized: true,
      initialize: jest.fn().mockResolvedValue(true),
      destroy: jest.fn().mockResolvedValue(true),
      createQueryRunner: jest.fn(),
    });

    // Compilar el árbol completo de dependencias
    testingModule = await moduleFixtureBuilder.compile();

    // Instanciar la aplicación para ejecutar hooks de ciclo de vida (onModuleInit)
    app = testingModule.createNestApplication();
    await app.init();
  });

  afterAll(async () => {
    if (app) {
      await app.close();
    }
  });

  it('debe compilar exitosamente el grafo completo de dependencias de AppModule', () => {
    expect(app).toBeDefined();
    expect(testingModule).toBeDefined();
  });

  it('debe registrar todos los controladores principales sin dependencias no resueltas', () => {
    // Validar resolución explícita de puntos de entrada críticos
    const controllers = [
      'AppController',
      'PatientController',
      'NotificationController',
      'BillingController',
    ];

    for (const controllerName of controllers) {
      const controllerInstance = app.get(controllerName, { strict: false });
      expect(controllerInstance).toBeDefined();
    }
  });
});
```

### Paso 2: Validación estricta de variables de entorno con Zod

El guardrail de inyección de dependencias debe complementarse con la validación de configuración en el arranque. Si un servicio requiere una variable de entorno y esta no existe, la aplicación debe fallar de forma inmediata (*fail-fast*) durante la compilación del módulo:

```typescript
// src/config/env.schema.ts
import { z } from 'zod';

export const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']),
  PORT: z.coerce.number().default(3000),
  DATABASE_URL: z.string().url(),
  JWT_SECRET: z.string().min(32, 'El secreto JWT debe tener al menos 32 caracteres para seguridad'),
  EXTERNAL_SMS_API_KEY: z.string().min(1, 'API Key de SMS requerida'),
});

export type EnvConfig = z.infer<typeof envSchema>;

export function validateEnv(config: Record<string, unknown>): EnvConfig {
  const parsed = envSchema.safeParse(config);
  if (!parsed.success) {
    const errorDetails = parsed.error.issues
      .map((issue) => `[${issue.path.join('.')}] ${issue.message}`)
      .join('\n');
    throw new Error(`Configuración de entorno inválida en el arranque:\n${errorDetails}`);
  }
  return parsed.data;
}
```

Integrado en `AppModule`:

```typescript
// src/app.module.ts
import { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config';
import { validateEnv } from './config/env.schema';
import { PatientModule } from './modules/patient/patient.module';
import { NotificationModule } from './modules/notification/notification.module';
import { AuditModule } from './modules/audit/audit.module';

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      validate: validateEnv,
    }),
    AuditModule,
    NotificationModule,
    PatientModule,
  ],
})
export class AppModule {}
```

## Resultados y métricas: Confiabilidad sin sacrificar velocidad en CI

Al incorporar esta prueba en la batería de verificación previa a la construcción de contenedores Docker, obtienes ventajas cuantitativas inmediatas:

| Métrica de Ingeniería | Tests Unitarios Tradicionales | Pruebas E2E Completas | Bootstrap Guardrail |
|---|---|---|---|
| **Tiempo de ejecución en CI** | 100 - 300 ms | 45 - 180 segundos | **350 - 500 ms** |
| **Infraestructura externa requerida** | Ninguna (Mocks en memoria) | Base de datos, Redis, Red | **Ninguna** (Adaptadores nulos) |
| **Detección de dependencias rotas en DI** | 0% (Punto ciego total) | 100% | **100%** |
| **Momento de detección de fallos** | N/A (Pasa en falso verde) | En stage o producción | **En pull request / pre-push** |
| **Falsos positivos por fallos de red** | 0% | Alto (Timeouts de servicios) | **0%** |

En nuestras aplicaciones en producción, la inclusión del Bootstrap Guardrail eliminó por completo los incidentes de despliegue asociados a `Nest can't resolve dependencies` y dependencias circulares no advertidas. Cualquier omisión de un `export` o mala configuración de un token modular bloquea el pipeline en menos de un segundo.

## Cuatro reglas de oro para blindar el arranque de tu backend

Para consolidar esta disciplina en tu equipo de desarrollo, establece estas reglas en tus estándares de ingeniería:

1. **Nunca asumas que un provider existe porque el mock funciona:** El hecho de que `mockPatientService` responda con datos de prueba no significa que el contenedor real sepa cómo instanciar `PatientService` en producción.
2. **Exporta explícitamente cada provider reutilizable:** Si un servicio será consumido fuera de su módulo de origen, agrégalo tanto a `providers` como a `exports`. Documenta la frontera modular.
3. **Ejecuta el Bootstrap Guardrail en cada Pull Request:** Agrega la prueba de arranque a la etapa más temprana de tu pipeline de CI. Si el contenedor no puede armarse en memoria, no tiene sentido construir imágenes de Docker ni ejecutar pruebas más complejas.
4. **Valida la configuración con esquemas estrictos al inicio:** No permitas que la aplicación arranque con variables de entorno nulas o malformadas. Falla rápido en el primer milisegundo antes de atender la primera conexión de red.

La cobertura de código es una métrica útil para evaluar la exhaustividad de tus pruebas unitarias sobre reglas de dominio, pero no sustituye la verificación estructural de tu arquitectura. Compilar tu contenedor real en CI es la diferencia entre un despliegue tranquilo y una emergencia en producción a las cinco de la tarde.
