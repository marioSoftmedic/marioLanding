El martes a las 11:40 de la mañana, un usuario en Santiago subió la fotografía de una orden médica a nuestro agente de WhatsApp en Examya. 

El pipeline visual procesó el documento sin fricción: reconoció un hemograma completo y un perfil lipídico, extrajo los códigos arancelarios de FONASA, cotizó los exámenes en la red de laboratorios asociados y le presentó el resumen de la compra junto con el total a pagar. La máquina de estados finitos (FSM) de la sesión avanzó al estado `CONFIRMING_ORDER`.

El sistema esperaba una confirmación para generar el enlace de pago seguro. Pero el usuario no escribió "Sí" ni "Confirmar". Escribió:

> *"¿Atienden los sábados en la sucursal de Providencia?"*

Lo que ocurrió en los siguientes 800 milisegundos destruyó la venta y la experiencia del paciente: el router de intenciones clasificó el mensaje como `FAQ_GENERAL_INQUIRY`. Como el estado `CONFIRMING_ORDER` de nuestra FSM ingenua solo tenía transiciones válidas para `CONFIRM` o `CANCEL`, el manejador por defecto no supo qué hacer con el contexto transaccional. La sesión sufrió un reinicio catastrófico a `START`.

El bot respondió amablemente: *"Atendemos de lunes a sábado de 7:30 a 13:00 hrs. ¡Hola! Bienvenido a Examya. Envía una foto de tu orden médica para comenzar"*.

Todo el carrito clínico —la imagen procesada por OCR, los códigos FONASA mapeados y el cálculo del copago— se evaporó de la memoria operativa. Para el usuario, el bot acababa de sufrir amnesia total.

Este fallo no es un caso aislado ni un error de redacción de prompts. Es el **síndrome del reinicio transaccional**: la incapacidad estructural de una máquina de estados rígida para absorber el diálogo conversacional asincrónico sin destruir el progreso del usuario.

```text
ESTRUCTURA INGENUA (COLAPSO ANTE PREGUNTAS LATERALES):

[Usuario sube orden] ──> [OCR & Cotización] ──> [CONFIRMING_ORDER]
                                                        │
                         "¿Atienden los sábados?"       │
                                                        ▼
[START / WELCOME] <──── [Fallback no controlado] <──────┘
(Estado destruido, carrito clínico borrado a cero)
```

## La trampa de las FSM lineales en canales conversacionales

Cuando trasladas flujos de e-commerce web a WhatsApp, el primer instinto arquitectónico suele ser modelar una máquina de estados determinística donde cada paso exige una respuesta unívoca.

En un navegador web, el usuario está contenido por una interfaz gráfica: si está en el paso de checkout, solo puede hacer clic en "Pagar", "Volver" o cerrar la pestaña. Pero en WhatsApp no hay botones obligatorios ni pantallas modales. La interfaz es una caja de texto libre donde conviven simultáneamente tres dimensiones de interacción:

1. **La intención transaccional primaria:** Avanzar en el embudo (confirmar, pagar, ingresar el RUT).
2. **Las dudas accesorias u off-topic:** Horarios de atención, condiciones de ayuno, cobertura geográfica o métodos de pago aceptados.
3. **Las correcciones contextuales:** Aclaraciones sobre mensajes anteriores (*"Me equivoqué en el RUT, el mío termina en K, no en 9"*).

```text
INTERACCIÓN REAL EN WHATSAPP:

   Transaccional:       [Confirmar orden] ─────────────┐
                                                       │
   Off-Topic / Duda:    [¿Atienden los sábados?] ──────┼──> [Caja de texto libre]
                                                       │
   Corrección / Ruido:  [Me equivoqué en el RUT...] ──┘
```

Si tu máquina de estados trata cualquier entrada no estrictamente transaccional como un error de transición (`InvalidTransitionError`) y redirige el flujo al inicio o a un fallback destructivo, estás castigando al usuario por interactuar de forma humana.

Para construir un sistema resiliente en producción, debíamos lograr que el agente respondiera la duda accesoria con precisión y, en el mismo turno conversacional, preservara el estado intacto y reinyectara el recordatorio del paso pendiente.

```text
PATRÓN DE PRESERVACIÓN RESILIENTE:

[CONFIRMING_ORDER] ──> "¿Atienden los sábados?" ──> [Interceptor Off-Topic]
        │                                                    │
        │ (Estado preservado en PostgreSQL)                  ▼
        │                                           [1. Responde duda]
        │                                           [2. Reinyecta STAGE_TASK_HINT]
        ▼                                                    │
[CONFIRMING_ORDER] <─────────────────────────────────────────┘
(El usuario mantiene su cotización y responde "Sí" en el siguiente mensaje)
```

## El bug sutil de JavaScript: límites de palabra `\b` y acentos en español

Antes de implementar el interceptor general, auditamos por qué fallaban ciertas confirmaciones explícitas en producción. Descubrimos un bug clásico pero traicionero en el motor de expresiones regulares de JavaScript (V8).

Teníamos una guarda rápida para capturar confirmaciones afirmativas sin invocar al clasificador LLM:

```typescript
// ❌ CÓDIGO VULNERABLE: Falla en español con caracteres acentuados
const AFFIRMATIVE_REGEX = /\b(si|confirmo|dale|ok|pagar)\b/i;

export function isDirectConfirmation(message: string): boolean {
  return AFFIRMATIVE_REGEX.test(message);
}
```

A primera vista parece inofensivo. Pero en JavaScript, el ancla `\b` (word boundary) evalúa el límite entre un caracter de palabra `\w` (`[a-zA-Z0-9_]`) y un caracter que no pertenece a `\w`.

En el estándar ASCII, los caracteres acentuados como `á`, `é`, `í`, `ó`, `ú` o la letra `ñ` no forman parte de `\w`. Pertenecen a `\W`.

Cuando un usuario escribía `"Sí, confirmo"`, ocurría lo siguiente:
- En `"sí"`, la letra `s` es `\w` y la letra `í` es `\W`.
- El motor evalúa que entre `s` e `í` **ya existe un límite de palabra**.
- La expresión `\b(si)\b` no coincide con `"sí"` porque busca la letra `i` latina sin tilde.
- Y si intentas usar `/\b(sí)\b/i`, el segundo `\b` busca una transición entre `\w` y `\W`, pero `í` ya es `\W`, haciendo que el matching falle si va seguido de puntuación o espacios inmediatos.

```typescript
console.log(/\bsi\b/i.test("sí")); // false
console.log(/\bsi\b/i.test("si")); // true
```

Al fallar la coincidencia determinística por un simple tilde en `"sí"`, el mensaje era derivado al clasificador de intenciones basado en LLM. En mensajes cortos con signos de exclamación o ruido tipográfico (*"¡¡sí claro!!"*), el router semántico devolvía una confianza marginal (`confidence: 0.48`), cayendo en la rama de baja certeza y bloqueando la confirmación de la orden.

### La solución con límites de puntuación Unicode

Reemplazamos las anclas `\b` por aserciones de posición basadas en límites de puntuación y espacios compatibles con Unicode (`flag u`):

```typescript
// ✅ CÓDIGO CORREGIDO: Compatible con tildes, signos de apertura y puntuación
const UNICODE_AFFIRMATIVE_REGEX = /(?:^|[\s,.;:¡!¿?])(si|sí|confirmo|confirmar|dale|ok|pagar|proceder)(?=$|[\s,.;:¡!¿?])/iu;

export function isDirectConfirmation(message: string): boolean {
  return UNICODE_AFFIRMATIVE_REGEX.test(message);
}
```

## La trampa de la normalización destructiva de cadenas

Un problema similar destruía el estado durante la captura de identificadores de identidad, como el Rol Único Tributario (RUT) chileno requerido para emitir la cotización con aranceles de FONASA.

En una iteración previa, el middleware aplicaba una limpieza agresiva sobre el texto antes de validar el formato:

```typescript
// ❌ CÓDIGO DESTRUCTIVO: Borra el contexto semántico del mensaje
export function extractRutDestructive(rawMessage: string): string {
  // Elimina todo lo que no sea dígito o letra K
  const cleaned = rawMessage.replace(/[^0-9kK]/g, "");
  return cleaned;
}
```

Si el usuario enviaba estrictamente `"12345678-9"`, la función retornaba `"123456789"`, pasaba el algoritmo de Módulo 11 y el flujo continuaba.

Pero los pacientes reales en WhatsApp escriben mensajes explicativos:
> *"Disculpa la demora, el RUT de mi madre es 14.285.714-2 gracias"*

Al aplicar `rawMessage.replace(/[^0-9kK]/g, "")` sobre ese texto, la cadena resultante era:
`"demoraelRUTdemimadrees142857142"` → filtrado a dígitos y K: `"142857142"` (o secuencias contaminadas si el texto contenía letras K o números en la frase). 

Peor aún: si el usuario enviaba una pregunta legítima durante el paso de solicitud de RUT (*"¿Aceptan RUT provisorio de recién nacido?"*), la limpieza destructiva transformaba el texto en una cadena vacía o en un fragmento inválido. El validador fallaba, arrojaba un error de validación genérico y reiniciaba la máquina de estados.

```typescript
// ✅ CÓDIGO RESILIENTE: Extracción no destructiva mediante tokenización y regex focalizada
const RUT_PATTERN = /(\d{1,2}\.?\d{3}\.?\d{3}-?[\dkK])/i;

export interface ExtractedRutResult {
  found: boolean;
  rawRut?: string;
  normalizedRut?: string;
  isValidChecksum: boolean;
}

export function extractAndValidateRut(message: string): ExtractedRutResult {
  const match = message.match(RUT_PATTERN);
  if (!match) {
    return { found: false, isValidChecksum: false };
  }

  const rawRut = match[1];
  const cleanRut = rawRut.replace(/[\.\-]/g, "").toUpperCase();
  const body = cleanRut.slice(0, -1);
  const dv = cleanRut.slice(-1);

  const isValid = validateRutModulo11(body, dv);

  return {
    found: true,
    rawRut,
    normalizedRut: `${body}-${dv}`,
    isValidChecksum: isValid,
  };
}

function validateRutModulo11(body: string, expectedDv: string): boolean {
  let sum = 0;
  let multiplier = 2;

  for (let i = body.length - 1; i >= 0; i--) {
    sum += parseInt(body[i], 10) * multiplier;
    multiplier = multiplier === 7 ? 2 : multiplier + 1;
  }

  const remainder = 11 - (sum % 11);
  let computedDv = "";
  if (remainder === 11) computedDv = "0";
  else if (remainder === 10) computedDv = "K";
  else computedDv = remainder.toString();

  return computedDv === expectedDv;
}
```

La extracción no destructiva desacopla la captura de datos de la intención global del mensaje. Si el usuario incluye texto explicativo, extraemos el dato relevante de forma limpia. Y si no hay ningún RUT presente, el sistema sabe que el mensaje debe evaluarse como una consulta o aclaración sin corromper el estado de la sesión.

## El patrón de resiliencia: `OFF_TOPIC_PURCHASE_STAGES` y `STAGE_TASK_HINT`

Para resolver de raíz el síndrome del reinicio transaccional, definimos dos estructuras fundamentales en el núcleo de la FSM de Shuri:

1. **`OFF_TOPIC_PURCHASE_STAGES`:** Un conjunto inmutable de estados transaccionales donde el usuario tiene una tarea crítica en curso.
2. **`STAGE_TASK_HINT`:** Un diccionario de mensajes de reenganche diseñados para recordarle al usuario el paso pendiente después de responder su duda accesoria.

```typescript
export enum OrderState {
  START = "START",
  AWAITING_PRESCRIPTION = "AWAITING_PRESCRIPTION",
  PROCESSING_OCR = "PROCESSING_OCR",
  AWAITING_EXAM_SELECTION = "AWAITING_EXAM_SELECTION",
  AWAITING_RUT = "AWAITING_RUT",
  AWAITING_ADDRESS = "AWAITING_ADDRESS",
  CONFIRMING_ORDER = "CONFIRMING_ORDER",
  AWAITING_PAYMENT = "AWAITING_PAYMENT",
  ORDER_COMPLETED = "ORDER_COMPLETED",
  CANCELLED = "CANCELLED",
}

// Estados donde una pregunta lateral NO debe reiniciar el flujo
export const OFF_TOPIC_PURCHASE_STAGES: ReadonlySet<OrderState> = new Set([
  OrderState.AWAITING_EXAM_SELECTION,
  OrderState.AWAITING_RUT,
  OrderState.AWAITING_ADDRESS,
  OrderState.CONFIRMING_ORDER,
  OrderState.AWAITING_PAYMENT,
]);

// Recordatorios contextuales inyectados al final de la respuesta off-topic
export const STAGE_TASK_HINT: Record<OrderState, string> = {
  [OrderState.START]: "",
  [OrderState.AWAITING_PRESCRIPTION]: "\n\n📄 Para cotizar tus exámenes, por favor envía una foto clara de tu orden médica.",
  [OrderState.PROCESSING_OCR]: "\n\n⏳ Estamos procesando tu orden, te responderemos en unos segundos.",
  [OrderState.AWAITING_EXAM_SELECTION]: "\n\n📋 ¿Deseas cotizar todos los exámenes identificados o prefieres seleccionar algunos?",
  [OrderState.AWAITING_RUT]: "\n\n🆔 Para aplicar tu cobertura de salud y emitir la cotización formal, por favor indícanos tu RUT.",
  [OrderState.AWAITING_ADDRESS]: "\n\n📍 Para verificar la cobertura de toma de muestra a domicilio, indícanos tu comuna o dirección.",
  [OrderState.CONFIRMING_ORDER]: "\n\n💡 Para avanzar con la reserva de tus exámenes, ¿confirmas la solicitud para enviarte el enlace de pago seguro?",
  [OrderState.AWAITING_PAYMENT]: "\n\n💳 Puedes completar tu pago de forma segura en el enlace que te enviamos previamente.",
  [OrderState.ORDER_COMPLETED]: "",
  [OrderState.CANCELLED]: "",
};
```

### La arquitectura del Interceptor Conversacional

Cuando entra un mensaje del usuario, el orquestador evalúa el estado actual de la sesión antes de tomar decisiones destructivas. El flujo de ejecución sigue tres compuertas determinísticas:

```text
ENTRADA DE MENSAJE
       │
       ▼
¿Es cancelación explícita? (isDenial) ───[SÍ]──> Transición a CANCELLED
       │ [NO]
       ▼
¿Cumple la acción esperada del estado? ──[SÍ]──> Transición normal de negocio
       │ [NO]
       ▼
¿El estado actual está en OFF_TOPIC_PURCHASE_STAGES?
       │
       ├────[SÍ]──> 1. Responder duda (RAG / FAQ / Reglas)
       │            2. Concatenar STAGE_TASK_HINT[currentState]
       │            3. Preservar estado y payload en PostgreSQL
       │
       └────[NO]──> Derivar a enrutador general / Menú principal
```

A continuación se muestra la implementación del despachador en TypeScript:

```typescript
export interface SessionContext {
  userId: string;
  currentState: OrderState;
  orderPayload: Record<string, unknown>;
  updatedAt: Date;
}

export interface DispatchResult {
  replyMessage: string;
  nextState: OrderState;
  payloadModified: boolean;
}

export async function handleUserMessage(
  message: string,
  session: SessionContext,
  knowledgeBase: KnowledgeService
): Promise<DispatchResult> {
  const currentState = session.currentState;

  // 1. Evaluación de cancelación explícita
  if (isExplicitDenial(message)) {
    return {
      replyMessage: "Entendido, hemos cancelado la gestión de esta orden médica. Si necesitas cotizar nuevamente en el futuro, solo escríbenos.",
      nextState: OrderState.CANCELLED,
      payloadModified: true,
    };
  }

  // 2. Evaluación de coincidencia transaccional según el estado
  if (currentState === OrderState.CONFIRMING_ORDER && isDirectConfirmation(message)) {
    const paymentUrl = await generateSecurePaymentLink(session.orderPayload);
    return {
      replyMessage: `¡Excelente! Tu cotización está lista. Puedes realizar el pago seguro en el siguiente enlace:\n${paymentUrl}`,
      nextState: OrderState.AWAITING_PAYMENT,
      payloadModified: true,
    };
  }

  if (currentState === OrderState.AWAITING_RUT) {
    const rutResult = extractAndValidateRut(message);
    if (rutResult.found && rutResult.isValidChecksum) {
      session.orderPayload.rut = rutResult.normalizedRut;
      return {
        replyMessage: `RUT ${rutResult.normalizedRut} validado con éxito. Calculando copago según arancel FONASA...`,
        nextState: OrderState.CONFIRMING_ORDER,
        payloadModified: true,
      };
    }
  }

  // 3. Interceptación Off-Topic con preservación de estado
  if (OFF_TOPIC_PURCHASE_STAGES.has(currentState)) {
    // Consultar el sistema de conocimiento para responder la duda puntual
    const faqAnswer = await knowledgeBase.answerInquiry(message);
    const hint = STAGE_TASK_HINT[currentState];

    // Respuesta combinada: Resuelve la inquietud + orienta a la acción
    const combinedReply = `${faqAnswer}${hint}`;

    return {
      replyMessage: combinedReply,
      nextState: currentState, // ESTADO INTACTO
      payloadModified: false,  // PAYLOAD PRESERVADO
    };
  }

  // 4. Fallback estándar para estados no transaccionales
  return {
    replyMessage: "¡Hola! Para ayudarte con tus exámenes de laboratorio, por favor envíanos una foto de tu orden médica.",
    nextState: OrderState.START,
    payloadModified: false,
  };
}
```

## Separación de negación explícita (`isDenial()`) del fallback orientador

Un peligro recurrente al implementar interceptores de preguntas laterales es confundir una negación o rechazo con una duda casual.

Si un usuario escribe *"No entiendo qué es el hemograma"*, el sistema **no debe** interpretar la palabra *"No"* como una orden de cancelación. Pero si el usuario escribe *"No quiero seguir, cancela esto"*, el sistema debe respetar su voluntad de inmediato y no insistir con recordatorios de pago.

Diseñamos una función de discriminación estricta para evitar falsos positivos de cancelación:

```typescript
// Expresiones de rechazo explícito y cancelación
const EXPLICIT_CANCELLATION_PATTERNS = [
  /^(no|cancelar|cancela|detener|ya no quiero|olv[ií]dalo)$/i,
  /^(no quiero|no deseo|no voy a) (continuar|pagar|seguir|comprar)/i,
  /cancelar (la )?(orden|solicitud|cotizaci[oó]n|pedido)/i,
];

// Expresiones que contienen 'no' pero representan dudas o aclaraciones
const NON_CANCELLATION_INQUIRIES = [
  /no s[eé]/i,
  /no entiendo/i,
  /no tengo (la orden|rut|dinero|tiempo)/i,
  /no puedo (ir|abrir)/i,
];

export function isExplicitDenial(message: string): boolean {
  const trimmed = message.trim();

  // Si coincide con un patrón de duda, NO es cancelación
  for (const inquiryPattern of NON_CANCELLATION_INQUIRIES) {
    if (inquiryPattern.test(trimmed)) {
      return false;
    }
  }

  // Evaluar coincidencia con cancelación estricta
  return EXPLICIT_CANCELLATION_PATTERNS.some((pattern) => pattern.test(trimmed));
}
```

Esta separación garantiza que la empatía conversacional no anule el control del usuario sobre su proceso.

## La regla de oro para agentes de salud en producción

Construir agentes conversacionales para salud o e-commerce transaccional en WhatsApp exige entender una separación arquitectónica fundamental:

> **Determinismo estricto en la máquina de estados; flexibilidad empática en la capa de diálogo.**

El modelo de lenguaje (LLM) es una herramienta excelente para redactar respuestas amables, interpretar lenguaje natural desestructurado y sintetizar bases de conocimiento clínico. Pero **jamás debe gobernar las transiciones de estado de tu negocio ni gestionar la persistencia de una orden médica**.

Cuando mantienes la máquina de estados anclada de forma determinística en PostgreSQL y añades compuertas de interceptación que absorben las preguntas laterales de los pacientes, transformas un bot frágil en una experiencia de atención clínica sólida, confiable y humana.
