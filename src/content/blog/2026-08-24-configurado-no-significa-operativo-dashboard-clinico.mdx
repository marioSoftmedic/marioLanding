## La ilusión del switch en verde

Son las 07:45 de la mañana en un laboratorio clínico. La fila de pacientes para toma de muestras comienza a crecer y el personal de admisión abre el panel de control. En la pantalla, un indicador luminoso brilla en verde esmeralda: "Pasarela de Respaldo: Activa". La interfaz transmite calma.

A las 08:12, la pasarela principal de pagos presenta un timeout intermitente debido a una congestión de red. El sistema debería conmutar de inmediato al proveedor secundario. Sin embargo, las órdenes médicas quedan congeladas, los copagos de FONASA no se liquidan y los mensajes de confirmación en WhatsApp dejan de salir.

Al inspeccionar los servidores, descubrimos la realidad: el switch verde en el panel solo indicaba que alguien había guardado las credenciales del proveedor de respaldo hace seis meses. El worker que debía procesar los reintentos estaba detenido por un error de dependencias, la suscripción del webhook secundario había expirado y jamás se había ejecutado una transacción de prueba en producción.

En sistemas críticos de salud, **configurado no es lo mismo que operativo**. Confundir ambos conceptos es uno de los riesgos invisibles más graves en la arquitectura de software médico.

## La trampa de la interfaz optimista

En el desarrollo de aplicaciones web convencionales, las interfaces optimistas son una práctica celebrada: el usuario presiona un botón, la interfaz actualiza el estado de inmediato para dar sensación de velocidad y la sincronización con el servidor ocurre en segundo plano.

En salud digital, este patrón sin salvaguardas es una trampa.

Una interfaz administrativa puede confirmar que una regla de ruteo, un canal de mensajería o un nodo de respaldo están "activos" simplemente porque el formulario local fue completado sin errores. Si la conexión falla antes del commit en la base de datos o si el backend no pudo instanciar el proceso en tiempo de ejecución, el operador se queda con una falsa sensación de seguridad. Al recargar la página minutos después, el cambio puede haber desaparecido o, peor aún, mostrarse como funcional cuando el motor subyacente está inerte.

Un indicador como la cobertura de turnos, la latencia de respuesta o el failover de comunicaciones no puede calcularse a partir de valores predeterminados fijados en un archivo de configuración. Debe derivarse estrictamente de **telemetría medida y eventos reales**.

## Los cuatro estados de verdad operacional

Para auditar y construir paneles de control verdaderamente confiables en Examya (donde coordinamos el procesamiento de órdenes médicas y mensajería multicanal con Shuri), separamos la verdad del sistema en cuatro capas explícitas:

```
[ 1. Configurado ] → [ 2. Persistido ] → [ 3. Activo ] → [ 4. Medido ]
  (Intención UI)       (Commit en BD)     (Worker vivo)    (Telemetría real)
```

1. **Configurado (Draft / Intent):** Los parámetros han sido ingresados por el operador en el cliente web. Representa la intención humana, pero no garantiza almacenamiento ni ejecución.
2. **Persistido (Stored):** Los datos han sido validados y guardados de forma atómica en la base de datos (PostgreSQL / Supabase) con sus respectivas restricciones de integridad.
3. **Activo (Runtime / Listening):** El proceso daemon, worker en NestJS o webhook de WhatsApp / Mercado Pago está inicializado, autenticado y escuchando eventos en tiempo de ejecución.
4. **Medido (Observed / Telemetry):** Existe evidencia reciente (latencia medida, pings de salud exitosos, transacciones completadas) dentro de una ventana móvil de tiempo (por ejemplo, últimos 5 minutos).

Si un servicio está en estado 2 (Persistido) pero falla en el estado 4 (Medido), el dashboard debe mostrar una advertencia clara: **"Configurado sin tráfico verificado"**, en lugar de un engañoso "100% Operativo".

## Modelando la evidencia en el sistema de tipos

Para evitar que el frontend asuma operatividad a partir de simples booleanos, modelamos el estado del servicio mediante tipos algebraicos estrictos en TypeScript:

```typescript
export type OperationalEvidenceLevel = 
  | 'CONFIGURED'  // Parámetros presentes en el cliente
  | 'PERSISTED'   // Almacenado en base de datos
  | 'ACTIVE'      // Proceso en runtime inicializado
  | 'MEASURED';   // Telemetría con transacciones reales en ventana T

export interface HealthTelemetryProbe {
  lastSuccessPing: Date | null;
  roundTripLatencyMs: number | null;
  errorRateWindow: number; // 0.0 a 1.0 en los últimos 15 min
  consecutiveFailures: number;
}

export interface ClinicalServiceState {
  serviceId: string;
  name: string;
  evidenceLevel: OperationalEvidenceLevel;
  telemetry: HealthTelemetryProbe;
  isReliableForTraffic: boolean;
}

export function evaluateServiceReliability(
  service: ClinicalServiceState,
  maxAllowedLatencyMs = 2500,
  maxErrorRate = 0.05
): boolean {
  // Regla estricta: solo se considera confiable si hay medición real
  if (service.evidenceLevel !== 'MEASURED') {
    return false;
  }

  const { lastSuccessPing, roundTripLatencyMs, errorRateWindow } = service.telemetry;

  if (!lastSuccessPing || roundTripLatencyMs === null) {
    return false;
  }

  const isRecent = Date.now() - lastSuccessPing.getTime() < 5 * 60 * 1000;
  const isPerformant = roundTripLatencyMs <= maxAllowedLatencyMs;
  const isHealthy = errorRateWindow <= maxErrorRate;

  return isRecent && isPerformant && isHealthy;
}
```

Al obligar al contrato de datos a exponer el nivel de evidencia (`evidenceLevel`) y las métricas de sonda (`HealthTelemetryProbe`), la interfaz de usuario no puede pintar un badge verde a menos que la función `evaluateServiceReliability` retorne verdadero con datos medidos en los últimos 5 minutos.

## El gotcha: la falsa garantía de los valores por defecto

Uno de los errores más frecuentes que encontramos al revisar arquitecturas legacy en salud es el uso de métricas "placebo" o valores estáticos en dashboards.

Por ejemplo, presentar un gráfico que dice "Disponibilidad: 99.9%" simplemente porque no se han registrado excepciones en la tabla de logs. Si la conexión a la pasarela de pagos estuvo caída durante la noche pero nadie envió una transacción para gatillar un error, la falta de logs de error no equivale a disponibilidad; equivale a **falta de observación**.

Una garantía operacional sin evidencia observable es únicamente una promesa no verificable, sin importar cuán pulida o moderna luzca la interfaz gráfica.

## Trazabilidad y auditoría clínica

En el contexto de la salud chilena, donde la Ley 21.668 exige interoperabilidad efectiva y el MINSAL avanza hacia estándares estrictos de continuidad asistencial, los registros operacionales deben ser demostrables.

Cuando una auditoría técnica o clínica revisa por qué una orden médica de urgencia demoró horas en autorizarse, no basta con argumentar que "el sistema figuraba encendido en el panel". Se requiere la traza inmutable de telemetría: cuándo se midió el último latido del servicio, cuál fue la latencia real y en qué milisegundo exacto el circuito de conmutación tomó el control.

Construir software para salud exige abandonar la comodidad de las interfaces complacientes y abrazar la disciplina de la evidencia continua.
