When an engineering team starts digitizing laboratory referrals between medical centers and clinical labs, the initial instinct is usually to model the network as a flat list: a database table storing laboratory names, API credentials, and a boolean flag indicating whether they are active.

On paper, this seems straightforward: an order arrives, the system queries the array of available providers, and dispatches the request to the first responsive endpoint.

However, that model collapses the moment the second institutional client is onboarded.

In B2B healthcare, a laboratory network is neither a public directory nor an open marketplace of interchangeable commodities. Each clinic, hospital, or corporate channel operates under specific commercial agreements, negotiated fee schedules, preferred providers by analytical specialty, and strict contingency protocols.

Treating the healthcare network as a flat list breaks clinical lineage and pushes business complexity into brittle code patches.

## The Breakdown of the Coupled Model

The most common architectural defect in digital health is concentrating four separate responsibilities into a single database entity named `Laboratory`:

1. **Provider Catalog:** What the laboratory is, where it is located, which technical protocols it supports (FHIR R4, REST, HL7 v2, SFTP), and its analytical capabilities.
2. **Institutional Membership:** Which healthcare institutions or channels are authorized to refer samples to it, and under what priority rules.
3. **Routing Authority:** Which system component holds the authority to decide where a given order should be routed.
4. **Commercial Agreements:** Which fee schedule applies, agreed turnaround times, and contractual terms.

```text
Coupled Model (Anti-pattern):
┌─────────────────────────────────────────────────────────────┐
│ Laboratory Object                                           │
│ ─────────────────────────────────────────────────────────── │
│ - ID / Name / Technical Endpoints                          │
│ - Linked Client Institution (rigid FK)                      │
│ - Pricing schedules and fee lists                           │
│ - Hardcoded referral rules                                  │
│ - Fallback logic scattered across controllers               │
└─────────────────────────────────────────────────────────────┘
```

When these domains are coupled, friction is inevitable:
- If a reference laboratory serves ten clinics, either the record is duplicated ten times or convoluted boolean flags make system behavior unpredictable.
- If an intake agent or admission interface needs to route an order, it ends up making business decisions without proper context or authority.
- If a provider temporarily halts a specialized molecular panel, manual deactivation risks breaking workflows for institutions lacking configured fallbacks.

## Separating Catalog, Network, and Routing Authority

To address this challenge within Examya and Fhirex, we formally decoupled domain boundaries. A laboratory (`Laboratory`) is modeled strictly as a service provider with technical capabilities, while referral networks live in dedicated institutional entities.

We defined four distinct layers:

```text
Decoupled Architecture:

1. Global Catalog           ┌────────────────────────────────────────┐
                            │ Laboratory (Provider / Endpoints)      │
                            └────────────────────────────────────────┘
                                               ▲
                                               │ assigned to
2. Institutional Network    ┌──────────────────┴─────────────────────┐
                            │ InstitutionLabNetwork                  │
                            │ (Institution + Providers + examRules)  │
                            └────────────────────────────────────────┘
                                               ▲
                                               │ evaluated by
3. Routing Resolver         ┌──────────────────┴─────────────────────┐
                            │ LabRoutingResolver                     │
                            │ (Precedence: Channel > Institution >FB)│
                            └────────────────────────────────────────┘
                                               ▲
                                               │ queries
4. Clinical Intake / Flow   ┌──────────────────┴─────────────────────┐
                            │ Medical Order / ServiceRequest         │
                            └────────────────────────────────────────┘
```

### 1. The Global Catalog (`Laboratory`)
Represents the laboratory as a provider entity. It contains institutional identifiers, technical endpoint configurations (FHIR R4 server, secure credentials), supported service categories, and global operational status. It contains no customer-specific pricing or institutional routing logic.

### 2. The Institutional Network (`InstitutionLabNetwork`)
Represents the operational contract between an institution (or channel) and its authorized laboratory providers. Each network entry (`InstitutionLabProvider`) defines:
- Referral priority within the institution.
- Enabled status (`isActive`).
- Specific examination or specialty rules (`examRules`), such as routing molecular biology to Provider A and routine chemistry to Provider B.

### 3. The Resolution Engine (`LabRoutingResolver`)
The sole authority responsible for determining an order's destination. It evaluates requests through a deterministic precedence hierarchy:
1. Explicit channel override (if an operational priority rule applies).
2. Institutional rule by exam code or test category.
3. Default institutional provider based on priority.
4. Contingency fallback or manual triage routing.

## Defining the Referral Contract in TypeScript

To ensure admission agents and ingestion services do not make arbitrary decisions, the institutional contract is expressed through immutable, typed data structures:

```typescript
// Provider configuration contract within an institutional network
export interface InstitutionLabProvider {
  id: string;
  institutionId: string;
  laboratoryId: string;
  priority: number;
  isActive: boolean;
  examRules?: {
    allowedCategories?: string[];    // e.g. ["molecular", "toxicology"]
    excludedExamCodes?: string[];    // e.g. ["0301045"]
    directRoutingCodes?: string[];   // exclusive routing codes
  };
  createdAt: Date;
  updatedAt: Date;
}

// Routing resolution request and response contracts
export interface RoutingResolutionRequest {
  institutionId: string;
  channelId?: string;
  examCodes: string[];
  serviceCategory?: string;
  urgencyLevel?: "routine" | "urgent" | "stat";
}

export interface RoutingResolutionResult {
  status: "resolved" | "manual_review_required" | "no_provider_available";
  selectedLaboratoryId?: string;
  matchedRuleType?: "channel_override" | "exam_rule" | "institution_default" | "fallback";
  reason: string;
  routingAuditId: string;
}
```

By standardizing this contract, ingestion layers do not need to query raw database tables or infer business agreements. They invoke the resolver with order context and receive an auditable routing decision.

```typescript
// Resolver with strict precedence and audit logging
export class LabRoutingResolver {
  async resolveDestination(
    request: RoutingResolutionRequest,
    network: InstitutionLabProvider[]
  ): Promise<RoutingResolutionResult> {
    const activeProviders = network
      .filter((p) => p.isActive)
      .sort((a, b) => a.priority - b.priority);

    if (activeProviders.length === 0) {
      return {
        status: "no_provider_available",
        reason: "No active providers found in the configured institutional network.",
        routingAuditId: crypto.randomUUID(),
      };
    }

    // 1. Evaluate specific category or code-level rules
    for (const provider of activeProviders) {
      if (provider.examRules?.allowedCategories?.includes(request.serviceCategory ?? "")) {
        return {
          status: "resolved",
          selectedLaboratoryId: provider.laboratoryId,
          matchedRuleType: "exam_rule",
          reason: `Matched analytical category rule: ${request.serviceCategory}`,
          routingAuditId: crypto.randomUUID(),
        };
      }
    }

    // 2. Fall back to institutional default provider by priority
    const defaultProvider = activeProviders[0];
    return {
      status: "resolved",
      selectedLaboratoryId: defaultProvider.laboratoryId,
      matchedRuleType: "institution_default",
      reason: `Assigned to institutional default provider (priority ${defaultProvider.priority})`,
      routingAuditId: crypto.randomUUID(),
    };
  }
}
```

## Gotchas from the Field

Designing a decoupled architecture in code is straightforward; deploying it against the operational reality of healthcare centers reveals real-world constraints.

### 1. Persistence Does Not Equal Runtime Execution
A frequent pitfall is assuming that because a rule is persisted in a database (such as `examRules` in PostgreSQL), the system automatically governs all real-time traffic. In production environments, resolvers often run behind feature flags or coexist with legacy pipelines. Persisted rules do not guarantee universal runtime adoption.

### 2. Contingency Contracts Must Be Explicit
When an order finds no matching laboratory—due to an infrequent assay or overloaded providers—the system cannot return an unhandled 500 error or fail silently. The contract must explicitly define fallback behavior:
- Does it route to a manual triage queue for medical technologists?
- Does it reject the order with clear clinical coding for the requesting physician?
- Is there a configured backup provider?

Without an explicit contingency contract, operators revert to informal channels, breaking digital traceability.

### 3. Local Test Suites Do Not Replace Live Smoke Validation
During development, we built an automated test suite of 450 local unit and integration tests (37 in web services and 413 across Shuri components), validating network isolation, rule precedence, soft-deletion, and error boundaries.

These tests prove algorithmic correctness against specifications. However, they do not replace live smoke tests and operational telemetry in production environments. Rigorous local testing is a prerequisite, but healthcare governance is proven in production.

## Network Governance in the Chilean Ecosystem

In Chile, regulatory frameworks like Law 21.668 (clinical record interoperability) and Law 21.719 (personal data protection) require healthcare institutions to maintain strict control over where patient data resides and who is authorized to process it.

Clinics cannot delegate custody of medical orders to opaque routing algorithms based on hidden commercial incentives. Referral agreements, sample custody, and clinical accountability require clear, auditable technical boundaries.

When digital health systems enforce these boundaries:
- Reference laboratories integrate as specialized nodes without forcing clinics to replace existing core software.
- Healthcare institutions retain governance over commercial terms and operational priorities.
- Patients receive diagnostic results with clinical fidelity, regardless of whether testing occurred locally or at a specialized reference center.
