## El cementerio de notas en tu propio chat

Casi todo profesional con un teléfono en la mano comete el mismo hábito: tiene un chat consigo mismo en WhatsApp anclado arriba. Allí envía audios rápidos mientras camina, enlaces que leerá después, fotos de recibos y recordatorios de tareas urgentes.

Parece la herramienta de captura perfecta porque no exige autenticación, no pide sincronizar cuentas y ya está abierta en la pantalla durante todo el día.

Sin embargo, ese chat termina invariablemente como un agujero negro de datos desestructurados. A los tres días, buscar un dato específico entre cincuenta notas de voz y capturas de pantalla es imposible. No hay etiquetado temático, no hay extracción de compromisos y la búsqueda por texto falla por completo con los audios. La captura es instantánea, pero la recuperación es cero.

## La fricción invisible de las aplicaciones de notas

La respuesta tradicional del ecosistema de productividad personal (PKM) ha sido recomendar herramientas dedicadas como Obsidian, Notion o Logseq. Son soluciones excelentes para sentarse frente a un monitor a sintetizar y estructurar pensamiento a largo plazo.

El problema radica en la captura en movimiento:

1. Debe desbloquear el dispositivo y localizar la aplicación.
2. Esperar a que el motor móvil inicialice y sincronice el repositorio local o la nube.
3. Decidir en qué carpeta, base de datos o plantilla encaja la nota.
4. Escribir en un teclado virtual reducido mientras camina o sube a un vehículo.

Esa fricción de apenas quince segundos destruye el hábito. El usuario siempre regresa al camino de menor resistencia: abre WhatsApp y graba un audio de cuatro minutos con pensamientos dispersos.

Si deseamos convertir esa interacción cotidiana en un segundo cerebro confiable, la interfaz debe seguir siendo WhatsApp, pero el backend debe procesar, categorizar y devolver el conocimiento estructurado en segundos.

## Los límites reales documentados en julio de 2026

Al diseñar la arquitectura de este agente personal para usuario final en nuestra investigación técnica de julio de 2026, identificamos dos restricciones operativas impuestas por la infraestructura oficial de Meta:

Primero: las notas de voz que envían los usuarios llegan como contenedores de audio en formato OGG comprimidos con el códec OPUS. En conversaciones espontáneas, los usuarios no envían comandos cortos de diez segundos; envían monólogos de ocho, doce o quince minutos donde mezclan tareas laborales con listas personales.

Segundo: las URLs de descarga que entrega la WhatsApp Cloud API para acceder a esos archivos multimedia son efímeras. Tienen un token firmado con un tiempo de vida (TTL) estricto de exactamente cinco minutos. Si su cola de procesamiento demora más de trescientos segundos en atender el webhook, el enlace queda invalidado y el archivo es inaccesible.

## La arquitectura: streaming en Go sin tocar el disco

El reflejo habitual en muchos servidores web es descargar el archivo temporal a disco mediante `os.CreateTemp`, ejecutar un proceso externo y luego borrarlo. 

En un servicio de mensajería con tráfico concurrente, guardar archivos multimedia en el sistema de almacenamiento local es un antipatrón severo:

- **Riesgo de privacidad:** Las notas de voz de los usuarios contienen ideas confidenciales, planes financieros y datos personales. Dejar fragmentos en disco antes o después de un reinicio abrupto vulnera las garantías de privacidad.
- **Degradación de I/O y memoria:** Escribir y leer bloques de diez megabytes en almacenamiento efímero añade latencia innecesaria y desgasta contenedores sin disco persistente.
- **Cuello de botella en la ventana de cinco minutos:** Descargar primero a disco y luego abrir un segundo flujo de subida duplica el tiempo de transferencia.

En lugar de almacenar datos en disco, diseñamos una tubería en Go que conecta la descarga desde Meta directamente con la carga en la API File de Gemini mediante un `io.Pipe`:

```go
package audio

import (
	"context"
	"fmt"
	"io"
	"net/http"

	"github.com/google/generative-ai-go/genai"
)

// StreamAudioToGemini descarga desde Meta y sube a Gemini sin escribir en disco.
func StreamAudioToGemini(ctx context.Context, metaDownloadURL string, metaToken string, client *genai.Client) (*genai.File, error) {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, metaDownloadURL, nil)
	if err != nil {
		return nil, fmt.Errorf("error creando request a Meta: %w", err)
	}
	req.Header.Set("Authorization", "Bearer "+metaToken)

	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		return nil, fmt.Errorf("error conectando con WhatsApp Cloud API: %w", err)
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		return nil, fmt.Errorf("meta API devolvió estado HTTP %d", resp.StatusCode)
	}

	// Creamos un pipe en memoria: reader hacia Gemini, writer desde Meta
	pr, pw := io.Pipe()

	go func() {
		// Buffer de 64 KB en memoria para transferencia continua
		buf := make([]byte, 64*1024)
		_, copyErr := io.CopyBuffer(pw, resp.Body, buf)
		if copyErr != nil {
			_ = pw.CloseWithError(copyErr)
			return
		}
		_ = pw.Close()
	}()

	// Gemini consume directamente desde el io.Reader
	fileOptions := &genai.UploadFileOptions{
		DisplayName: "audio-note-transient",
		MIMEType:    "audio/ogg",
	}

	geminiFile, err := client.UploadFile(ctx, "", pr, fileOptions)
	if err != nil {
		return nil, fmt.Errorf("fallo al streamear audio hacia Gemini File API: %w", err)
	}

	return geminiFile, nil
}
```

El flujo consume el stream de bytes de forma continua. La nota de voz viaja en memoria por el canal HTTP sin persistir en el almacenamiento del servidor. Una vez que Gemini recibe el archivo y procesa la ventana multimodal de un millón de tokens, el buffer se descarta de inmediato.

## El gotcha: recordatorios en Asynq y la ventana de 24 horas

Una función indispensable en un segundo cerebro es la gestión de recordatorios y revisiones diferidas. Si el usuario le dice al agente un martes: *"Recuérdame revisar la cotización de los servidores el viernes a las 10:00 AM"*, el sistema debe programar esa tarea.

En nuestro backend gestionamos las tareas diferidas utilizando colas en Redis mediante la librería Asynq, registrando cada timestamp exclusivamente en formato UTC para evitar errores de desfase horario.

El problema técnico surge al ejecutar la tarea el viernes por la mañana:

WhatsApp impone una regla estricta de atención al cliente. Si han transcurrido más de veinticuatro horas desde el último mensaje enviado por el usuario, la sesión queda cerrada para mensajes de texto libre generados por un modelo de lenguaje. Si intenta enviar un mensaje estándar a través del endpoint `/messages`, Meta responde con el error `131047` (`Message failed to send because more than 24 hours have passed`).

Para entregar el recordatorio de forma legítima, el backend debe recurrir a una **Plantilla de Utilidad** pre-aprobada por Meta:

```go
package notifier

import (
	"context"
	"fmt"
	"time"
)

// DispatchReminder evalúa la ventana de 24 horas antes de emitir la notificación.
func DispatchReminder(ctx context.Context, client WhatsAppClient, phone string, lastSeen time.Time, reminderText string) error {
	const customerWindow = 24 * time.Hour

	// Si estamos dentro de la ventana de 24h, enviamos texto libre estructurado
	if time.Since(lastSeen) <= customerWindow {
		return client.SendTextMessage(ctx, phone, reminderText)
	}

	// Fuera de ventana: obligatorio usar Plantilla de Utilidad aprobada con variable {{1}}
	templateName := "recordatorio_segundo_cerebro"
	parameters := []string{reminderText}

	err := client.SendUtilityTemplate(ctx, phone, templateName, parameters)
	if err != nil {
		return fmt.Errorf("fallo al enviar plantilla de utilidad fuera de ventana: %w", err)
	}

	return nil
}
```

### El impacto en el modelo de costos

Esta restricción técnica impone un límite directo en el modelo económico del producto:

Cada plantilla de utilidad iniciada por la empresa fuera de la ventana de servicio tiene una tarifa por conversación que ronda los **$0.04 USD** (dependiendo del país de destino). Si un usuario programa quince recordatorios diferidos en el mes, esos mensajes representan un costo fijo en la factura de Meta cercano a $0.60 USD solo en transporte de mensajería.

Un agente personal no puede enviar notificaciones arbitrarias sin evaluar el presupuesto operativo. Es indispensable implementar filtros de consolidación diaria o umbrales de prioridad para que el sistema combine recordatorios menores en un solo resumen matutino y optimice el uso de plantillas.

## Zoom out: la ingeniería detrás de la aparente simplicidad

Construir un agente conversacional para el usuario final no consiste en conectar un prompt a una API y esperar que la magia ocurra. La experiencia de usuario parece invisible: el usuario graba un audio de diez minutos y recibe de vuelta una lista sintetizada con sus ideas clave y sus tareas agendadas.

Sin embargo, sostener esa interacción sin fricción exige resolver ingeniería dura:
- Consumo en streaming con pipelines de `io.Reader` para no colapsar la memoria ni violar la privacidad en disco.
- Control milimétrico de los TTLs de cinco minutos de Meta.
- Gestión de estados asíncronos y colas de tareas en UTC.
- Adaptadores de plantillas de utilidad para no quedar bloqueados por las políticas de mensajería.

La verdadera utilidad de un segundo cerebro no depende de la sofisticación del modelo que genera el texto, sino de la confiabilidad de las tuberías que transportan y custodian sus datos.
