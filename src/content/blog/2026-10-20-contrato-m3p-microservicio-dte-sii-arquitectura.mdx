Son las 10:15 de la mañana en una distribuidora de insumos agropecuarios y logísticos. Tres canales de venta operan en paralelo: un asesor en terreno registra pedidos desde una tableta, el portal mayorista procesa órdenes automáticas de clientes recurrentes y un agente de inteligencia artificial atiende solicitudes espontáneas por mensajería instantánea.

En cuestión de segundos, dos clientes distintos solicitan las últimas cuarenta unidades disponibles de un insumo crítico sujeto a control sanitario. El agente conversacional, diseñado con un modelo de lenguaje para responder con agilidad comercial, confirma la reserva de inmediato en el chat. Al mismo tiempo, el vendedor presencial emite la nota de venta en el terminal de bodega.

Si la arquitectura del sistema permite que el componente de inteligencia artificial interactúe directamente con las tablas de inventario o genere órdenes sin un protocolo transaccional determinístico, el resultado es inevitable: sobreventa de existencias físicas, bloqueo de despachos y una discrepancia contable que estalla en el momento de emitir la factura tributaria electrónica.

Integrar agentes autónomos en la operativa de un sistema de planificación de recursos empresariales (ERP) no es un problema de procesamiento de lenguaje natural. Es un desafío riguroso de arquitectura de software, concurrencia en bases de datos y soberanía regulatoria.

## Por qué los agentes de IA rompen los ledgers tradicionales

Los modelos de lenguaje son motores probabilísticos excelentes para interpretar la intención de un usuario, clasificar consultas desestructuradas y redactar respuestas comerciales fluidas. Sin embargo, los sistemas transaccionales y los libros contables exigen garantías completamente opuestas: determinismo absoluto, consistencia matemática y cumplimiento estricto de restricciones relacionales.

Cuando un equipo de ingeniería comete el error de exponer endpoints de mutación directa o herramientas de ejecución de base de datos a un agente sin un cortafuegos formal, surgen tres vectores de falla operativa:

1. **Mutaciones desalineadas con reglas de negocio:** El modelo puede interpretar que una confirmación verbal de un cliente constituye una orden de venta firme, pasando por alto validaciones financieras como límites de crédito aprobados o listas de precios preferenciales vigentes.
2. **Condiciones de carrera en inventario:** Si la reserva de existencias se maneja como una simple actualización de campos (`UPDATE stock SET cantidad = cantidad - $1`), dos ejecuciones paralelas del agente o un cruce con ventas manuales generarán inconsistencias de stock negativo.
3. **Pérdida de trazabilidad forense:** Resulta imposible reconstruir ante una auditoría si una alteración en la base de datos provino de un operario humano autorizado, de una regla automática del sistema o de una alucinación del modelo en una conversación ambigua.

Para mitigar estos riesgos sin renunciar a la agilidad de los agentes, la arquitectura debe imponer una separación estricta: los agentes proponen intenciones de negocio, pero solo una capa intermedia de contratos de datos inmutables y tipados puede validar, autorizar y persistir eventos en el núcleo del ERP.

## El protocolo M3P: contratos inmutables como cortafuegos

En el diseño de nuestra plataforma para distribuidoras (`erp-distribution`, conocido internamente como "Los Tres Mosqueperros"), estructuramos este desacoplamiento mediante el protocolo M3P (Modular Multi-Party / Message Protocol). 

M3P opera como una especificación estricta de contratos de mensajería donde cada transición operativa —solicitud de cotización, reserva temporal, validación de crédito y autorización de despacho— se modela como un evento inmutable con esquema tipado.

En nuestra implementación de referencia en código (`demo/js/datos.js`), definimos 22 firmas de contratos tipados que cubren el ciclo completo de la distribución. La lógica del agente (`demo/js/agente.js`) estructura 9 patrones de interacción que traducen el diálogo con el cliente en una carga útil que debe satisfacer formalmente la firma antes de ingresar a la cola transaccional:

```typescript
// Definición de interfaz de contrato inmutable M3P para reserva de inventario
export interface M3POrderIntentEvent {
  eventId: string;
  timestamp: string;
  sourceAgentId: string;
  customerId: string;
  items: Array<{
    sku: string;
    requestedUnits: number;
    unitPrice: number;
  }>;
  regulatoryMetadata: {
    requiresPrescription: boolean;
    prescriptionId?: string;
  };
  signature: string;
}

export function validateOrderIntent(event: M3POrderIntentEvent): boolean {
  if (!event.eventId || !event.customerId || event.items.length === 0) {
    return false;
  }
  if (event.regulatoryMetadata.requiresPrescription && !event.regulatoryMetadata.prescriptionId) {
    return false; // Bloqueo determinístico: falta prescripción regulatoria
  }
  return true;
}
```

Al utilizar esta interfaz, el agente conversacional no tiene privilegios de escritura sobre el motor transaccional. Su única facultad es emitir un `OrderIntentEvent`. Si el cliente no suministró la información requerida o si los valores no respetan los tipos de datos esperados, el contrato rechaza la carga antes de tocar la base de datos.

## Concurrencia y mitigación de sobreventas en PostgreSQL

Una vez que el contrato M3P valida la estructura y precondiciones de la solicitud, el procesamiento transaccional debe garantizar que las existencias físicas no se comprometan en exceso ante solicitudes concurrentes.

En la migración de arquitectura hacia PostgreSQL y servicios en Fastify, abordamos esta concurrencia mediante transacciones con nivel de aislamiento controlado y bloqueo pesimista a nivel de fila (`SELECT ... FOR UPDATE`):

```sql
-- Bloqueo pesimista en PostgreSQL para mitigar sobreventas concurrentes
BEGIN;

SELECT sku, stock_disponible, stock_reservado
FROM inventario_bodega
WHERE sku = 'AGRO-BIO-098' AND bodega_id = 'BOD-CENTRAL'
FOR UPDATE;

-- El motor bloquea la fila hasta completar la transacción:
-- Si el stock disponible es insuficiente para cubrir la solicitud, se revierte.
UPDATE inventario_bodega
SET stock_reservado = stock_reservado + 40,
    stock_disponible = stock_disponible - 40
WHERE sku = 'AGRO-BIO-098' AND bodega_id = 'BOD-CENTRAL' AND stock_disponible >= 40;

INSERT INTO ledger_eventos_inventario (evento_id, sku, tipo, unidades, timestamp)
VALUES ('evt-847294', 'AGRO-BIO-098', 'RESERVA_M3P', 40, NOW());

COMMIT;
```

Este enfoque traslada la responsabilidad de la coherencia transaccional al motor de base de datos relacional. El agente puede enviar cientos de intenciones concurrentes, pero el bloqueo pesimista en la transacción garantiza que cada reserva se evalúe secuencialmente contra el balance real, rechazando de forma segura cualquier solicitud que exceda la disponibilidad física.

## Safety gates regulatorios: el control fitosanitario SAG (Test B1.5)

En la distribución especializada en Chile —particularmente en los sectores agrícola, veterinario y químico—, la operación no solo responde a reglas comerciales, sino a normativas estatales estrictas supervisadas por el Servicio Agrícola y Ganadero (SAG).

Ciertos productos químicos y biológicos exigen retención inmediata de despacho a menos que el cliente adjunte una receta profesional emitida por un médico veterinario o ingeniero agrónomo acreditado. Si un sistema automatizado permite que un agente de ventas confirme y despache un producto restringido sin esa receta, la empresa incurre en infracciones legales severas.

Para blindar esta frontera, integramos un *safety gate* regulatorio en `demo/js/agente.js`, formalizado y verificado mediante la prueba técnica `Test B1.5` de nuestra suite:

- Cuando un cliente solicita un SKU catalogado con control fitosanitario, el validador del contrato M3P inspecciona el metadato regulatorio.
- Si el campo `prescriptionId` no está presente y verificado, el sistema ejecuta una transición de estado hacia `RETENIDO_POR_RECETA_SAG`.
- Se bloquea de forma determinística la generación de la guía de despacho y se notifica al canal de mensajería la necesidad de subir el documento oficial antes de liberar la mercadería.

Es imperativo delimitar la madurez técnica de este componente con total honestidad de ingeniería: este mecanismo de retención está plenamente **implementado y probado en código y pruebas locales** (`Test B1.5`). Sin embargo, no constituye una auditoría oficial presencial del SAG en terreno ni certifica infalibilidad administrativa en faena, hitos que dependen de procesos de fiscalización regulatoria institucional.

## El microservicio DTE SII: soberanía tributaria sin SaaS lock-in

Superada la validación de inventario y el cumplimiento normativo de despacho, la última etapa crítica del ERP es la facturación electrónica ante el Servicio de Impuestos Internos (SII) de Chile, regulada bajo la Resolución Exenta N° 45/2003 y sus especificaciones técnicas vigentes.

La mayoría de las empresas recurre a intermediarios SaaS de facturación que exponen APIs REST propietarias. Aunque esta alternativa reduce el esfuerzo inicial de integración, introduce dependencias operativas y financieras complejas a medida que el volumen transaccional escala:

- **Costos marginales crecientes:** Los proveedores cobran tarifas en UF o suscripciones escalonadas con costos recurrentes por cada folio emitido.
- **Punto único de falla:** Si la API del intermediario sufre degradación o interrupciones de red, el centro de distribución queda paralizado sin poder emitir guías de despacho (DTE 52) ni facturas (DTE 33), impidiendo la salida física de camiones de reparto.
- **Riesgo de soberanía de datos:** La información comercial y tributaria de clientes y precios reside en infraestructura de terceros ajenos a la organización.

Para superar este desacoplamiento, diseñamos la arquitectura de un **microservicio interno de Documentos Tributarios Electrónicos (DTE)** que interactúa directamente con los protocolos del SII.

```
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│   Agentes IA /  │ ----> │    Capa M3P     │ ----> │   Kernel ERP    │
│  Canales Venta  │ (M3P) │ (22 Contratos)  │       │  (PostgreSQL)   │
└─────────────────┘       └─────────────────┘       └────────┬────────┘
                                                             │ Evento Facturación
                                                             ▼
                                                    ┌─────────────────┐
                                                    │ Microservicio   │
                                                    │    DTE SII      │
                                                    │ ─────────────── │
                                                    │ • Canonical C14N│
                                                    │ • Firma XMLDSig │
                                                    │ • Timbre (TED)  │
                                                    │ • Validación CAF│
                                                    └────────┬────────┘
                                                             │ SOAP / REST
                                                             ▼
                                                    ┌─────────────────┐
                                                    │ SII (Ambiente   │
                                                    │    Palena)      │
                                                    └─────────────────┘
```

El pipeline de procesamiento del microservicio interno ejecuta las siguientes etapas determinísticas:

1. **Construcción y canonicalización XML (C14N):** Transforma la orden de venta validada en el documento XML estandarizado por el SII, aplicando canonicalización para que el formato textual no sufra alteraciones por saltos de línea o espacios.
2. **Firma digital criptográfica (XMLDSig):** Firma el nodo `Documento` utilizando el certificado digital comercial (X.509 v3) de la empresa mediante el algoritmo SHA-1 con RSA, garantizando la autoría e integridad del emisor.
3. **Inyección de CAF y generación de Timbre Electrónico (TED):** Acopla el Código de Autorización de Folios (CAF) provisto por el SII y calcula la firma electrónica del timbre tributario, generando la matriz de código de barras bidimensional en formato PDF417 exigida para la representación gráfica impresa.
4. **Validación de esquema XSD y transmisión:** Verifica el documento contra el esquema oficial del SII antes de empaquetar el envío en un contenedor SOAP/REST para su transmisión al ambiente de pruebas.

Nuevamente, corresponde trazar la frontera técnica con rigor: este microservicio DTE se encuentra **diseñado y especificado técnicamente**, con pruebas de generación y validación de esquemas ejecutadas en el ambiente de certificación Palena del SII. La obtención de la resolución exenta definitiva como emisor electrónico en producción real y las pruebas de estrés bajo concurrencia masiva corresponden a etapas de validación operativa planificadas. Disponer de este software no exime de fiscalización tributaria ni garantiza aprobaciones instantáneas sin apego riguroso a las especificaciones del SII.

## Arquitectura desacoplada: lecciones de trinchera

Construir software para la operativa física de distribución enseña una lección fundamental de arquitectura: **la inteligencia artificial debe ser un observador y proponente de negocio, jamás el custodio directo del estado del sistema**.

Al articular este proyecto, consolidamos tres principios aplicables a cualquier equipo de ingeniería que construya sobre ERPs modernos:

- **Contratos tipados sobre lenguaje natural:** Nunca permita que un modelo decida qué datos persistir. Establezca un catálogo estricto de eventos (como nuestras 22 firmas M3P) y rechace toda carga útil que no supere la validación sintáctica y semántica.
- **Determinismo transaccional en la persistencia:** Delegue la concurrencia a transacciones ACID robustas en PostgreSQL con bloqueos pesimistas en las tablas de inventario para evitar sobreventas accidentales.
- **Soberanía en infraestructura crítica:** Internalizar componentes como el microservicio DTE del SII requiere comprender la criptografía y los esquemas regulatorios del Estado, pero elimina tarifas transaccionales recurrentes y otorga control absoluto sobre la continuidad operacional.
